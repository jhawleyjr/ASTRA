## Repository findings (read at `be32cbb`)

- `RunLog::discard` (`:410`) deletes the file at two init sites: the provenance write failure in the `RunLog`

## Joe's decisions in this planning session (2026-09-29)

These refine the M6 contract. **D1 and D2 are deviations from the approved M6 plan's wording**, decided by Joe.

- **D1, init cleanup.** This is a deviation from the M6 plan's "the core never deletes a log file". The core
  never deletes a log file, with one exception: the `.partial` that this `from_config` call created
  exclusively. It is deleted only while that same call is failing, never after the call returns. The
  destructor and `close_log()` delete nothing. A stale `.partial` refused at construction was not created by
  the call and is never touched. There are two current sites: the `RunLog` constructor's provenance write
  failure, and the transport `open()` failure in `open_log_and_transport`. Any future init step after the
  create follows the same rule. Disclosed residual: the delete goes by name, so something could rename a file
  over that name between the create and the delete (up to the handshake timeout). There is no device or inode
  check. PR 2 tests it: a failed handshake leaves neither `log.path` nor the `.partial`, and a refused stale
  `.partial` stays byte-identical (R16b).
- **D2, the kill window.** This narrows the wording of the approved outcome.
  - (a) After each block's flush, a per-group `rows_committed` attribute is set. It changes only on
    row-count boundaries, so byte identity holds across drain patterns. At close it ends equal to the group's
    row count, and `load` checks that on a finalized log. If HDF5 writes it to disk early, that is still
    safe, because it names only rows flushed before it was set.
  - (b) `load(allow_incomplete=True)` trusts only rows below `rows_committed`. It raises a typed error naming
    the group in three cases: `rows_committed` exceeds either dataset's extent; the trusted `frame` column is
    not exactly 0, d, 2d, …; or a chunk covering trusted rows of `frame` or `values` is unallocated (h5py's
    chunk info).
  - (c) The stated limit. Without single-writer/multiple-reader mode (SWMR), HDF5 orders nothing inside a
    flush. It can write dirty metadata to disk in the middle of an append, and it rewrites some metadata in
    place: chunk-index nodes split when a chunk is inserted (under the 1.8 low bound the index is expected to
    be a version-1 B-tree; **PR 2 confirms**). So a kill during a block write (the append) or its flush,
    during close, or during the destructor can in principle damage rows that were already certified. "Never
    wrong data" holds for a kill outside those windows. Inside them it is guarded by (b), which turns the
    failures we can name into refusals. The R16 kill tests are evidence, not proof.
  - SWMR is the rejected alternative that would make the guarantee absolute. It needs the 1.10 format as the
    low bound, allows no new objects once it starts (`/writes`, `/summary` and `/final_state` are created at
    close), and would need the byte-identity story redone.
- **D3, the destructor.** It runs `close_log()`'s sequence with two differences: no rename, and
  `finalized_by = "destructor"` set last, where `close_log()` sets `complete`. The tails get their flush and
  their `rows_committed` update, and everything is flushed before the marker. After any earlier failure (a
  failed drain, or `kLog`), it writes nothing more and sets no marker, so a missing marker means the run was
  killed or failed. The destructor may never run (interpreter exit without collection, abort, a kill), and
  such a file is treated as killed. `load(allow_incomplete=True)` reports the finalization state (complete,
  destructor or incomplete). It exposes `/summary` and `/final_state` only when `complete` or the marker is
  present, and applies the cross-checks to both. Otherwise it returns certified rows only. `replay` refuses
  any file without `complete` and says which of the other two states it found. A kill during the destructor's
  close falls under the same stated limit as a kill during `close_log()`.
- **D4, the `.partial` name.** Without `allow_incomplete`, `load` refuses a path whose resolved name ends in
  `.partial`, naming "not published by close_log()". The check follows symlinks, and it is a guard, not a
  proof (a hard link is not detected). To keep the rule unambiguous, the core refuses a `log.path` ending in
  `.partial` with a `ConfigError` naming `log.path`, and replay's `out` follows the same rule. With
  `allow_incomplete=True`, a `.partial` holding `complete = 1` is reported as complete but unpublished and
  exposes everything, with the cross-checks applied. A second `close_log()` after a refused publication
  raises the same error again and does not retry the rename. A user who clears the collision moves the file
  by hand (`mv -n`).
- **D5, the format version.** `log_format_version` becomes 2, and `load` refuses version 1 (no `.h5` files are
  committed).

## Deliverable 1: `docs/decisions/0027-run-log-finalization.md` (Status: proposed)

**Related/supersedes:** it supersedes ADR-0025's **Finalization** section only, and ADR-0025 is not edited. It
adds to ADR-0025's Enabling (more refusals), Replay (the `out` rules) and Determinism (the fallback does not
cover this record) without contradicting them. Decision items:

1. **Where a log is written (Q19, D4).** At construction, `log.path` is made absolute, or its parent directory
   is held open as a directory descriptor. The create, the publication rename and D1's delete all use that, so
   a change of working directory mid-run cannot redirect publication or deletion. Each of these is refused
   with a `ConfigError` naming `log.path`:
   - an existing `log.path` (a dangling symlink counts);
   - an existing `<log.path>.partial` (a stale partial is the user's, and is never opened, changed or deleted);
   - a `log.path` ending in `.partial`.

   Otherwise the log creates `<log.path>.partial` exclusively in the same directory, writes the provenance and
   flushes. An unwritable or missing directory fails the create, which is also a `ConfigError`.
2. **Crash-readable writing (Q18, D2).** After every block write of any group, on the drain path and the close
   path alike (tails included), the writer flushes and then sets that group's `rows_committed`.
   - **Why the call sequence does not depend on the drain pattern (C-05).** `move_rows_to_blocks` merges rows
     oldest-first across groups, with a tie going to the smaller divisor. So blocks complete, and their
     flushes and `rows_committed` writes happen, in frame order, wherever the drain boundaries fall. The
     complete sequence of HDF5 calls is therefore a function of the config, the per-group row counts and the
     external writes only, including the tails and closing objects that close writes.
   - **Cost (C-18, N-03).** One flush and one attribute write per block, and one after the provenance.
     Session's per-frame drains flush only when a block completes. PR 2 measures the cost (R19b) against the
     1001 s gate and the 59.3 s pytest run.
3. **Explicit close.** The sequence:
   1. the tails, each with its flush and `rows_committed`;
   2. `/writes`, `/summary` and `/final_state`;
   3. the group handles closed, then a flush;
   4. `complete = 1`, the last write;
   5. the file's close;
   6. `renameat2(RENAME_NOREPLACE)`, publishing to `log.path`.

   Every refusal raises a `LogError` naming the path and the reason, and the `.partial` stays. It never falls
   back to a non-atomic path, and it is idempotent without a retry (D4). A file at `log.path` is one that
   `close_log()` completed and published, and nothing else. A published log carries no finalization attribute.
4. **Destructor (Q17, D3).** `Session` calls `close_log()` on its normal close.
5. **What a killed run leaves.** The table below; D2(c) states the limit.

   | Where the kill lands | What is left |
   |---|---|
   | before the create | nothing |
   | after the create, before the provenance flush returns | a file that may not open, which `load` refuses |
   | no block write in progress | the certified prefix |
   | during a block write or its flush | the stated limit, guarded by D2(b) |
   | during close or the destructor | the stated limit, guarded by D2(b) |

   The certified prefix loses at most, per group, the ring rows, the staging tail and one block. The guarantee
   covers a process kill with the OS intact: no fsync.
6. **`load`.** The three states, whether the file is published, strict refusal of a `.partial` name, and the
   cross-checks on both finalized states: `final_state.frame == frames_run`; the groups' signal names equal
   `/summary`'s names, each once; and `rows_committed` equals each group's row count. The trusted frame column
   is expected to be exactly 0, d, 2d, … for every complete log, including a halted run that is stepped again
   (**PR 2 confirms**).
7. **Replay.** It refuses anything without `complete` and names the state. `out` follows item 1, and replay
   publishes through `close_log()`.
8. **Who deletes what (N-01, D1).** A tool deletes only files its own invocation created, and never a refused
   or collided file.
9. **Determinism (C-05).** ADR-0025's byte-identity criterion is unchanged, and its fallback is not available
   here. A failure of R18 goes back to Joe.
10. **Format version 2 (D5).**
